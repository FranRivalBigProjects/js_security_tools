What This JavaScript Vulnerability Scanner Detects

Static analysis cannot catch all vulnerabilities — runtime behavior, user input paths, and server-side issues require dynamic testing. But static scanning reliably catches dangerous patterns that account for the majority of JavaScript security issues in production code.

Critical //

XSS Sinks

Detects dangerous assignments: innerHTML, outerHTML, document.write, insertAdjacentHTML. These inject raw HTML and are the primary XSS vectors in modern JS applications.

Critical //

Unsafe eval Usage

Flags eval(), Function(), setTimeout/setInterval with string arguments. Executing strings as code is a direct RCE/XSS path if any part of the input is user-controlled.

High //

Prototype Pollution

Detects assignments to __proto__, Object.prototype, and dynamic property merges that can poison all objects. Critical in Node.js — can lead to privilege escalation.

High //

DOM-Based Sources

Flags reads from location.hash, location.search, document.referrer, document.cookie — common sources for DOM XSS when data flows to a sink without sanitization.

Medium //

Hardcoded Secrets

Detects patterns matching API keys, tokens, passwords, and AWS credentials in JS code. Secrets in client-side code are publicly exposed to anyone who views source.

Medium //

Insecure Randomness

Math.random() is not cryptographically secure — never use it for tokens, session IDs, or security-sensitive values. Use crypto.getRandomValues() instead.

What Developers Ask About JavaScript Vulnerability Scanning

What is the difference between static and dynamic JavaScript vulnerability scanning?
Static analysis (what this tool does) reads your code without executing it — finding dangerous patterns, sink assignments, and known-bad API usage. It's fast and works on any code, but can produce false positives and misses runtime behavior. Dynamic scanning executes the application and observes real behavior — like actual XSS payload injection or prototype pollution via API calls. Production-grade security requires both: static scanning in your IDE/CI pipeline and dynamic testing (DAST) against a running application. Tools like Burp Suite, OWASP ZAP, or Snyk provide dynamic scanning.

How do I fix innerHTML XSS vulnerabilities in JavaScript?
Replace element.innerHTML = userInput with element.textContent = userInput for plain text content. For rich content, use the DOMParser sanitization approach or the Sanitizer API (Chrome 93+). As a last resort, use a library like DOMPurify: element.innerHTML = DOMPurify.sanitize(userInput). Never build HTML strings by concatenation with user input — even escaping is error-prone compared to using the DOM API directly.

How do I detect if my JavaScript has been compromised (supply chain attack)?
Supply chain attacks inject malicious code into npm packages or CDN-hosted libraries. Mitigation: use Subresource Integrity (SRI) hashes on script tags to verify CDN content hasn't changed, pin exact versions in package.json (not ranges), run npm audit on every install, use Snyk or Socket.dev to monitor dependencies for new CVEs, and implement a strict Content Security Policy that blocks unexpected external script origins.

Why is Math.random() insecure for generating tokens?
Math.random() is a pseudorandom number generator (PRNG) seeded by a predictable value. An attacker who observes several outputs can reconstruct the internal state and predict future values — making any token generated with it forgeable. Use crypto.getRandomValues() (browser) or crypto.randomBytes() (Node.js) — both use the OS's cryptographically secure random source. This applies to session tokens, CSRF tokens, reset links, and any security-sensitive random value.
